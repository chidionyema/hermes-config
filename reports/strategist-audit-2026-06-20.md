## 🔴 Issues (act today)

### R1. `reflect-on-correction.py` is broken (P0) — emits identical templated noise every 30 min

**Evidence:**
- `~/.hermes/scripts/reflect-on-correction.py` lines 67–77: "Root cause of this correction" + "Fix applied" + "--- auto-generated by reflect-on-correction hook ---" are **hardcoded strings**.
- It runs unconditionally as Phase 0.5 of the idle-learning pipeline (every 30 min via cron `3fcdc6bd8859`).
- Result: `~/.hermes/logs/reflection/2026-06-19.md` has **39 identical "Auto-Reflection" entries**, `2026-06-20.md` has **13** as of 08:02 UTC. Each claims "Policy 004 has 0 hits and confidence 0.3" — but pol-004 was already promoted to active / confidence 0.8 on day 1. The reflection is lying every 30 min.
- Falsely claims "Hook runs automatically after every correction event" — but no correction event ever fires; the script runs on idle schedule, not on corrections.
- pol-004 is a 1-hit active policy now, but the reflection loop is spamming 26+ times/day making the daily reflection useless and inflating policy-004's apparent volume in the firings list.

**Fix:** Replace the hardcoded template with actual diffing. The script should:
1. Read the last 24h of `policy-firings.jsonl` and only fire on **new** firings (not just "any firing exists").
2. Compute actual root cause by diffing policy hit counts vs previous snapshot — not copy a fixed string.
3. If no new firing → exit silently (no reflection entry).

**This is a structural defect, not a doc issue.** The script must be edited, not annotated.

### R2. `idle-continuous-learning` cron is erroring 319× (false-positive) — silent, never resolved

**Evidence:**
- watchdog.jsonl shows 319 historical `IDLE_ERROR: idle-continuous-learning errored: Script timed out after 120s` alerts.
- The last **actual** idle-learning-runs.jsonl entry with `exit != 0` is `2026-06-18T19:30:24` (Phase 0 + Phase 4). All 19 runs since then completed (exit 0) or were preempted (exit 0, reason=preempted).
- The watchdog is firing on the 120s hard kill by the scheduler as a CRON_ERROR even though the script's own bookkeeping marks the run as `preempted` (i.e., designed exit-on-preempt). The "preempted" reason is a normal operating state, not a failure.
- This means **319 false alarms** are drowning signal in the watchdog log (1MB+ jsonl, 4092 lines).

**Fix:** In `watchdog.py`'s CRON_ERROR classifier, treat `Script timed out` + reason=`preempted` as `healthy=true` and suppress the alert. Or: lower the cron hard cap below the pipeline's MAX_RUNTIME so the script can `exit 0 preempted` cleanly.

### R3. `health-watchdog` is itself errored — self-unwell monitor

**Evidence:**
- `cron/jobs.json` shows `abf69d5df846 health-watchdog` last_status=`error`, last_error="Script exited with code 1".
- The error is `⚠️ 1 alert(s) open >= 3 runs (unhealed): GIT_DIRTY: 295 uncommitted files`.
- The watchdog exits non-zero when it has unhealed alerts. That's **by design** in its contract — exit 0 = healthy, exit 1 = has alerts. But cron treats exit 1 as error and re-fires the watchdog again in 15 min.
- Combined with R2 above, the watchdog is compounding noise, not surfacing it.
- The watchdog's `last_run_at: 2026-06-20T08:01:09` shows it IS still running and writing alerts — so functionally it's working, just nominally "errored."

**Fix:** Decide which one is true. Either:
- (a) Exit 0 when alerts exist but logged, exit 1 only on watchdog's own internal failure (probe timeouts, can't write log). This is the right contract.
- (b) Add a wrapper that captures exit 1, checks for the "alerts: [...]" stdout content, and re-maps to exit 0 for cron purposes.
